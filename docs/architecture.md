# Архитектура Creator Hero Bot

## Стек

- **Python 3.12** + **aiogram 3.x** (Bot API, long polling)
- **SQLite** через **SQLAlchemy 2 (async, aiosqlite)**; миграции — **Alembic**. Переход на Postgres позже = смена URL + драйвера (docker-compose уже готовит место под это)
- **APScheduler 3.x** (AsyncIOScheduler) — джобы по расписанию
- **pydantic-settings** — конфигурация из env
- Деплой: **Docker + docker-compose**
- Тесты: **pytest + pytest-asyncio**

## Запуск

Один процесс: polling + планировщик в одном event loop. Long polling — серверу не нужен публичный URL/SSL. Джобы создаются/пересоздаются при старте и при изменении потока (singleton-процесс, джобы не дублируются).

## Модель данных

> Мультипоточность заложена сразу: `stream_id` есть во всех таблицах. Деление на «потоки» в v1 не используется — одна запись-поток создаётся миграцией/командой.

```
streams        id, title, chat_id (unique), invite_link, timezone,
               settings_json, is_active, created_at
participants   id, stream_id→streams, tg_user_id (null до /start),
               username, full_name,
               status (approved|active|left|kicked|revoked),
               joined_at, left_at, kick_count
daily_reports  id, stream_id, participant_id, report_date (локальная дата),
               message_id, kind (link|forward|text), char_count,
               seq_number (№k за день), created_at
               UNIQUE(stream_id, participant_id, report_date)
penalties      id, stream_id, participant_id, reason (missed_report),
               issued_for_date, status (open|paid|expired|cancelled),
               issued_at, paid_at, paid_message_id, due_at
daily_counters stream_id, report_date, emoji, count   -- эмодзи дня + №k
```

## Ключевые потоки

### Приём `#пост` (handler → services.challenge)
1. Сообщение в группе, содержит `#пост`, автор — активный участник.
2. Edited-сообщения игнорируем (античит, как у оригинала).
3. Валидация: текст/подпись ≥ `MIN_POST_CHARS` **или** ссылка t.me **или** форвард из канала. Не прошло → реплай с подсказкой.
4. Идемпотентность: один отчёт на (stream, user, дата). Повторный — реплай «уже засчитано».
5. Записываем, инкрементим счётчик дня. Для первого принятого отчёта участника
   случайно выбираем реплай: с вероятностью 80% «№k из N + эмодзи дня»,
   с вероятностью 20% «вау, справилось k из N героев! ⚡️», как в Content Hero.
   Номер и число активных участников подставляются из результата зачёта.
   Повторный отчёт не выбирает новое подбадривание: остаётся ответ «уже засчитано».

### День → ночь (джобы, таймзона потока, по умолчанию Europe/Moscow)
- Владелец Telegram-чата (`creator` в Bot API) не участвует в групповых
  обязательствах: не входит в N и статистику, не получает напоминаний, новых штрафов
  и киков. Его прежние отчёты и штрафы сохраняются в БД, но исключаются из дайджестов
  и статистики. Роль проверяется через `getChatAdministrators` по Telegram ID;
  обычные администраторы остаются участниками. Это роль самого чата, независимо
  от настроенного `OWNER_TG_ID` для команд управления. Если роль определить
  не удалось, джоба пропускает действия для потока и пишет предупреждение в лог.
  Если за закрываемый день нет участников с обязательствами, пустой дайджест
  в чат не публикуется (включая чат только с владельцем).
- **18:00** — напоминание всем, кто не сдал (реплай/пост в группу со списком).
- **00:00** — закрытие дня: несдавшим без открытого штрафа выставляется `penalty`
  (due = +24ч), публикуется `#дайджест`. У участника в потоке максимум один открытый
  штраф: новые пропуски не суммируют долг и не продлевают его срок. Ограничение
  закреплено уникальным индексом БД; после отработки возможен новый штраф за новый день.
- **20:00** — напоминание штрафникам с open-штрафами (группа; личка — v1.1).
- **00:05** — кик участников с просроченными штрафами (`status=kicked`; без unban — возврат только через `/approve` владельцем).

### Приём `#штраф`
Хештег + автор имеет open-штраф → `status=paid`, реплай-подтверждение. Факт доната не проверяем (как оригинал).

### Онбординг (whitelist)
1. Владелец в личке бота: `/approve @username` → участник `approved`. Для `kicked` — это же команда возврата (unban + сброс штрафов). `/revoke @username` — убрать из whitelist (для `approved`, не трогая вступивших).
2. Пользователь пишет боту `/start` в личке: если его юзернейм в whitelist → приветствие + бессрочная инвайт-ссылка на чат. Не в whitelist → вежливый отказ («челлендж закрытый, вас пока нет в списке»).
3. Пользователь вступает по ссылке → `active`, приветствие в группе. При первом
   вступлении бот просит представиться с хештегом `#обомне` и написать свою
   `#цель`, чтобы другие участники познакомились с новичком. Это знакомство, а не обязательный
   отчёт: эти хештеги не засчитываются как `#пост` и отдельно не проверяются.
   Первый вход определяется по отсутствию сохранённого `joined_at` до активации;
   повторные события входа уже активного участника не дублируют приветствие.

### Выход/возврат (механика «свободной паузы»)
- Участник выходит из чата сам → `left`. Пока `left` — обязательств нет, джобы его пропускают (не попадает в N, напоминания, штрафы). Новые штрафы за дни вне чата не начисляются — даже если вышел на 5 минут в 23:55 (**осознанное решение: эксплойт «тактический выход» принят как фича, аудитория — друзья**).
- При возврате без открытых штрафов бот приветствует с возвращением по `@username`
  (или по имени, если username отсутствует), без повторной просьбы о знакомстве. История входа сохраняется
  также после кика и повторного `/approve`; смена username не делает участника новичком,
  поскольку его находят по привязанному Telegram ID. Постоянная ссылка остаётся прежней.
- **Открытый штраф НЕ аннулируется при выходе.** Возврат по бессрочной ссылке →
  `active`, единственный открытый штраф получает новый
  `due_at = возврат + PENALTY_GRACE_HOURS` — сначала отработай `#штраф`, иначе кик
  по стандартному циклу. При таком возврате приветствие содержит напоминание о долге
  и сроке отработки. Дни вне интервалов членства не создают штрафов и при восстановлении
  после простоя: проверяется присутствие на дедлайн соответствующего дня.
- Накопленные Telegram updates обрабатываются перед запуском расписания.
  Пропущенные закрытия дней восстанавливаются по истории членства и отмечаются
  в `daily_closures`. При первом запуске новой схемы автоматически закрывается
  только вчерашний день, если поток уже существовал.
  Автоматическая публикация дайджеста разрешена только за вчера по часовому поясу
  потока, если он ещё не отправлен. После простоя старые закрытия и штрафы
  восстанавливаются с учётом членства и ограничения одного открытого штрафа,
  но пачка прошлых дайджестов в чат не отправляется.
  Пропущенные старые сообщения не помечаются отправленными; при следующих запусках
  они также не публикуются.

### Кик и возврат после кика
- Кик = `banChatMember` **без** `unban`: участник остаётся в чёрном списке чата, инвайт-ссылка для него не работает.
- Возврат только через владельца: `/approve @username` в личке → бот делает `unbanChatMember`, статус `kicked → approved`, штрафы обнуляются; пользователь пишет боту `/start` и получает ссылку заново.

## Нефункциональное

- **Идемпотентность** везде: джобы перезапускаемы без двойных штрафов (проверка по статусам/датам).
- **Мягкая деградация**: бот не админ в чате → кик заменяется сообщением владельцу; ошибки отправки логируются, джоб не падает.
- **Логи**: structlog/logging в stdout → docker logs.
- Том SQLite — volume в compose, бэкап = копия файла.

## Личная цепочка уроков Creator Hero (33 дня)

Участник из whitelist активирует свою цепочку командой `/start` в личке бота.
Владелец Telegram-чата также исключён из автоматической доставки уроков; ранее
сохранённая история курса остаётся в БД.
Она запускается для `approved` или `active` только после надёжной привязки Telegram
ID. У каждого участника свой прогресс. Повторный `/start` не обнуляет цепочку;
смена username не передаёт её другому аккаунту. Неизвестные гости, удалённые из
whitelist и `kicked` не получают новую цепочку. Существующие участники после
обновления должны написать `/start`: миграция автоматически никого не записывает.

Первый урок приходит **через 10 минут после первой активации** `/start`. Следующие
уроки приходят в **08:00 МСК**, не раньше следующей московской даты после фактической
отправки предыдущего. По одному в день, в личке появляется короткий анонс
с кнопкой «Открыть урок». Всего 33 урока; полный текст и дополнительные материалы доступны публично в WriteFreely.
Чтение и маленькие шаги необязательны: дополнительной отчётности или штрафов нет.
Участник может получать уроки через 10 минут после `/start`, до вступления в общую группу.
В группе учебные сообщения не публикуются.

При `left` или `kicked` отправка приостанавливается. `/start` для `left` даёт
инвайт, но не отменяет паузу. После возвращения в группу (`active`) существующая
цепочка продолжается со следующего урока; сброса и пачки пропущенных уроков нет.
При `/revoke` ещё не вступившего участника привязанный к Telegram ID аккаунт
переходит в `revoked`: доступ и отправка остановлены, ID и прогресс сохранены.
`/start` отказывает, вход по общей ссылке оставляет человека гостем. `/approve`
возвращает тот же аккаунт в `approved`, сохраняя цепочку. Если username изменился,
владелец использует `/approve TelegramID`: команда восстанавливает только уже
привязанный аккаунт, без создания новой записи или передачи ID. `/revoke TelegramID`
также поддерживается. Неизвестный ID не создаёт нового участника. Удаляется только ещё
не привязанный whitelist контакт без учебного прогресса. Даже после отзыва доступа,
повторного одобрения или завершения всех 33 уроков `/start` не начинает курс заново.

После первого урока расписание всегда **08:00 Europe/Moscow**, независимо от часового пояса
сервера и настроек отчётов потока. Для первого урока ставится точный одноразовый таймер на `activated_at + 10 минут`.
При запуске будущие таймеры восстанавливаются из БД, а просроченные проверяются
обычным восстановлением доставки. Повторный `/start` не переносит время.
Планировщик также каждую минуту проверяет каждого активировавшего цепочку участника:
это восстановление после пропущенного таймера и путь повторов после 429. `course_runs` хранит дату личной активации и
первого урока (дата активации). Уникальная запись `(participant_id, lesson_day)` сохраняет попытку,
результат и время отправки в `lesson_deliveries`. Каталог `bot/data/lesson-catalog.json`
содержит 33 последовательных дня с проверенными HTTPS ссылками.

После простоя каждый участник получает максимум один следующий урок за местную
дату. Ещё не отправленный первый урок доступен после `activated_at + 10 минут`; остальные — начиная с 08:00.
Все уроки сохраняются в порядке, курс сдвигается; после
урока 33 отправка заканчивается. Фактическая дата успешного сообщения берётся из
ответа Telegram, чтобы медленный запрос через полночь не приводил к двум урокам
за одну дату. При запуске сначала обрабатываются накопленные Telegram updates,
затем восстанавливается закрытие отчётных дней и проверяются личные уроки.

Перед Telegram запросом бот фиксирует `sending` в БД. Успешный ответ сохраняется
как `sent` вместе с ID сообщения и временем. Ответ 429 означает явный отказ:
повтор возможен не раньше `retry_after`, отсчитанного от получения ответа.
Другие явные ошибки API, в том числе блокировка бота участником (403), сохраняются
как `failed` и требуют исправления. При сетевой ошибке/500 исход неизвестен
(`uncertain`); при аварии процесса останется `sending`. Бот не может обеспечить
атомарность между SQLite и Telegram `sendMessage`, у которого нет ключа
идемпотентности. Такие отправки автоматически не повторяются.

Владелец получает одно уведомление об остановке конкретного участника.
`/course_status @username` или `/course_status TelegramID` показывает его прогресс.
После проверки у участника `/resolve_lesson @username sent` отмечает урок
доставленным; следующий будет не раньше следующего утра. Если урока точно нет
и причина исправлена, `/resolve_lesson @username retry` явно разрешает повтор.
Вместо username можно использовать Telegram ID. Команда ждёт завершения ещё
идущего запроса. Ошибочное ручное решение может создать дубликат. Один
polling процесс остаётся обязательным условием работы.


### Проверка общей ссылки перед выдачей

Перед каждым разрешённым `/start` бот получает текущую основную ссылку чата через
`getChat.invite_link`. Именно Telegram служит источником актуального адреса:
сохранённый в `streams.invite_link` адрес обновляется при расхождении. Проверка
выполняется только для участников с разрешённым доступом, включая временно
вышедших (`left`), и не снимает бан.
Одновременные запросы в одном процессе последовательно обновляют одну запись.

Бот не редактирует, не создаёт, не отзывает и не перевыпускает ссылки при `/start`.
Ранее выданные дополнительные ссылки сохраняются; ограничения ссылок не меняются.
Если Telegram не вернул основную ссылку, недоступен, ограничил частоту или отклонил
запрос, бот просит повторить `/start` позже и не отправляет старый адрес из БД.
Неудачная проверка не изменяет сохранённую ссылку, курс уроков и его расписание.
